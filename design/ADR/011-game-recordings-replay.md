# ADR 011: Game State Snapshots and MQTT Trace Replay

## Status

Accepted

## Context

Debugging game issues requires reproducing exact game states. Testing card abilities and stage transitions needs repeatable setups. Demo recordings should replay with realistic timing. We needed both point-in-time snapshots and full session recordings.

## Decision

- **State snapshots**: Full game state serialized as JSON via `GET /state` or `SIGUSR1` signal, saved to `software/data/recordings/`. Snapshots capture board, hands, decks, graves, scores, lives, active stage, and round number.
- **MQTT trace recording**: `tracer.py` records input MQTT messages to a JSONL file with timestamps. Only input topics are recorded (`gwent/cards/raw/read`, `gwent/mfd/choose`) — output topics (sfx, display) are regenerated by the game on replay.
- **Replay**: `replay.py` reads a JSONL trace and publishes messages back onto the MQTT bus with real-time delays (capped at `MAX_DELAY = 20s`). The tracer is disabled during replay to avoid re-recording.
- **Loading snapshots**: A saved state JSON can be loaded at startup to jump directly to any game state, bypassing registration and dealing.
- Trace filename is set via `tracer.set_filename()`.

## Consequences

### Positive
- Can jump to any game state for targeted testing (e.g., start at round 3).
- Replay with timing produces realistic demo playbacks.
- Recording only inputs keeps trace files small and avoids redundant data.
- Snapshots are human-readable JSON — easy to edit for test scenarios.

### Negative
- Snapshots don't include MQTT message history — only current state.
- Replay assumes the same card data files exist; missing cards cause errors.

### Risks
- Schema changes to game state break loading of old snapshots; no automatic migration.
- Replaying against a different code version may produce different outcomes.
